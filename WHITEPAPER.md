# SinglePact Reactor: Transient Executability Locks for Objective-Centric Onchain Execution

**Draft:** 0.1.0  
**Status:** Pre-experiment working paper  
**Evidence ceiling:** X1 deterministic local fixture

## Abstract

Onchain execution is usually represented as transaction construction and submission. Users and autonomous systems, however, care about objectives that may depend on several independently changing conditions. The conditions may become jointly valid only briefly, and transaction submission does not itself prove the objective was achieved. Reactor proposes a Simultaneous Executability Lock: an immutable binding of authenticated, compatible condition versions and exact execution parameters created during a valid overlap. This repository currently provides a deterministic local fixture for lock semantics and experimental design. It does not yet provide measured Solana, Jito, or MagicBlock evidence.

## 1. Transaction attempts and execution objectives

A transaction encodes one attempt. An objective defines the postcondition, authority, constraints, deadline, and evidence required for completion. Reactor separates the objective lifecycle from any single transaction.

## 2. The transient executability problem

An action may require price, liquidity, collateral health, market status, authority, and budget conditions to hold simultaneously. Independent updates can create a short common-validity interval. A delayed path can observe some or all of the component states yet fail to act while their exact versions remain compatible.

## 3. Existing execution approaches

This section will compare ordinary submission, keepers, schedulers, priority fees, bundles, intent solvers, and delegated execution environments. No comparative performance conclusion should be inserted before primary-source research and measured experiments are complete.

## 4. Reactor system model

Reactor uses Objective, Path, Pact, Session, State, Lock, Attempt, Proof, Receipt, and Gaia. The initial primitive is condition-centric and does not require multiple agents.

## 5. Simultaneous Executability Lock

A lock freezes the exact required condition versions, their common validity interval, and the bounded action configuration. Later updates remain live but cannot mutate the accepted lock.

## 6. Safety and failure model

The system must reject missing, stale, false, expired, incompatible, or replayed condition updates. It must prevent duplicate locks and distinguish submission, observation, verification, failure, and ambiguity.

## 7. Architecture

The target architecture consists of authenticated condition adapters, a delegated hot-State Session, deterministic lock evaluation, a base-layer action, and postcondition verification. The current repository implements only the deterministic local kernel.

## 8. Experimental method

Identical condition streams are supplied to baseline and Reactor paths. Overlap duration and reaction delay are varied. The primary metric is verified valid-window capture rate. False-lock rate must remain zero.

## 11. Limitations

Current limitations include fixture-only condition state, deterministic latency models, no external protocol integration, no reservation-economics measurement, no MagicBlock program, no Solana/Jito benchmark, no independent replication, and no demand validation.

## 12. Toward persistent objective execution

If transient locks prove valuable, the lifecycle can later support residual-objective calculation, re-arming, rerouting, reconciliation, bounded compensation, and verified closure. These are roadmap capabilities, not current implementation.

## 13. Conclusion

The present work defines a falsifiable mechanism and local semantic fixture. Its value remains conditional on measured evidence that representative objectives contain meaningful transient overlaps that optimized base-layer paths fail to capture reliably.
