# Reactor Thesis

**Version:** 0.1.0  
**Status:** Falsifiable hypothesis, not established fact

## Core thesis

Independently changing onchain conditions can form valuable executable configurations whose overlap is shorter than a conventional base-layer observe-build-submit path can reliably capture. A high-frequency delegated execution environment may detect that alignment, bind the exact compatible state versions into an immutable executability lock, and carry the resulting attempt toward verified settlement.

## Primary hypothesis

For representative, authenticated joint-executability windows shorter than the measured baseline observation-to-lock latency, Reactor will produce a materially higher **verified valid-window capture rate** than the strongest realistic baseline while producing zero false locks.

## Null hypothesis

After fair baseline selection, settlement latency, state-reservation requirements, and realistic workloads are included, Reactor does not materially improve verified capture rate.

## Supporting hypotheses

1. Multiple independently changing conditions can form short-lived compatible overlaps.
2. Some of those overlaps correspond to valuable executable objectives rather than synthetic timing loops.
3. Exact source versions can be frozen before the overlap disappears.
4. Later updates cannot mutate an accepted lock.
5. A lock can be carried into an attempt without being mislabeled completion.
6. Objective completion can be independently verified from postconditions.

## Alternative explanations

A measured Reactor advantage may actually be caused by:

- an intentionally weak baseline;
- synthetic condition expiry;
- colocating Reactor while placing the baseline remotely;
- using fixture-only state that cannot exist in a real protocol;
- excluding Jito or other optimized submission paths;
- pre-reserving resources so strongly that rapid alignment is no longer necessary;
- counting detected windows instead of verified outcomes;
- ignoring failed Magic Actions or stale external state.

## Kill or reframe conditions

Reactor must be killed or materially reframed when any of the following holds:

1. the strongest realistic baseline captures substantially the same valuable windows;
2. representative workloads rarely produce valuable sub-baseline overlaps;
3. the advantage appears only under deliberately manufactured expiries;
4. condition state cannot be authenticated, versioned, or safely reserved;
5. any false lock is accepted;
6. accepted locks frequently fail before objective verification;
7. reservation costs erase the execution value;
8. the claimed advantage disappears under independent replication.

## Durable thesis

Transactions are attempts, not objectives. If the transient-lock hypothesis survives, Reactor can become the first primitive in an objective-execution runtime that remains armed across changing conditions and, eventually, failed attempts.
